# 빠른 진행: 문항별 병렬 파이프라인

이 방식은 **문항마다 따로** 진행하고, **고칠 수 있는 반려는 그 자리에서 고치게** 한다. 그러면 전체 대기 시간이 "가장 느린 한 문항"만큼으로 줄어든다.
예전 방식은 묶음 단위로 진행했다. 출제자가 여러 문항을 순서대로 쓰고, 묶음 전체를 검토한 뒤, 반려된 문항은 2번째 시도부터 개념을 바꾼 대체 명세로 처음부터 다시 썼다. 걸린 시간 대부분이 재작성과 대기였다.

## 원칙
1. `plan` 직후 **문항마다 출제자 하위 에이전트를 하나씩 동시에** 띄운다. 30문항 이상이면 2문항씩 묶어도 된다.
2. 출제자는 자기 문항만 쓴다. 쓰고 `check`하고, 통과(`awaiting_review`)하면 바로 끝낸다.
3. 출제자가 끝나는 즉시 **그 문항의 검토자(새 하위 에이전트)**를 띄운다. 다른 문항을 기다리지 않는다.
4. 검토 결과는 `review --item N`으로 판정한다.
   - 출력이 `(같은 명세 — 고치기)`인 경우: 쉬움, 단순 읽기, 자료 없이 풀리는 진술, 사소한 교과 지적으로 반려된 것이다. **원래 출제자에게 이어서 지시**한다(SendMessage). 맥락이 남아 있어 금방 끝난다. 원래 출제자를 쓸 수 없으면 새 출제자를 띄우고 고치기 모드 brief를 읽게 한다.
   - 출력이 `(대체 명세 — 새로 쓰기)`인 경우: 정답 불일치나 심각한 모호성으로 반려된 것이다. 새 출제자를 띄운다.
5. 진행 상황은 `status --work W`의 "다음:" 열로 본다. 값마다 할 일이 다르다.
   - `write`·`repair`: 출제자가 쓴다.
   - `review`: 검토자가 푼다.
   - `judge`: `review` 명령을 실행한다.
   - `refill`: `refill` 명령을 실행한다.
   - `done`: 끝난 문항이다.
   - `--json`으로 받을 수도 있다.
6. 출제자는 자기가 쓴 문항을 검토하지 않는다. 검토자는 review-brief.md만 본다.
7. 엔진은 출제 중인 에이전트가 없을 때만 다시 빌드한다(`cd backend && npm run build:skill`). 빌드하는 동안 엔진 폴더가 잠깐 비기 때문이다.
8. 3회 모두 반려된 문항(`refill`)은 `exam refill`로 다시 연다. 다시 연 자리는 고치기 모드가 아니라 새 명세로 쓴다.

## 여러 개념 섞기
"이 개념들을 모두 넣어" 같은 요청은 `plan --lock --concepts "…"`로 한 번에 계획한다(단원을 넘나들어도 된다). 묶음을 나누거나 시드를 골라 개념을 맞출 필요가 없다. 엮을 개념 지시는 brief에 들어 있으니 출제자 프롬프트에 따로 적지 않아도 된다.

## 출제자 프롬프트 (문항마다)
```
너는 수능 직업탐구 <성공적인 직업생활|공업 일반> 출제위원이다. 스킬 <skill-dir>/SKILL.md의 "문항 쓰기"(1~4단계)만 수행하라. 블라인드 검토는 하지 마라.
작업 폴더 <W>, 담당 문항 <N>번만 맡는다. 다른 문항은 다른 에이전트가 동시에 작업 중이니 건드리지 마라.
items/<NN>/brief.md를 끝까지 읽고, 끝의 "제출 전 자기 점검" 7항목을 하나씩 확인한 뒤 candidate.json을 저장하라.
그다음 `node <skill-dir>/scripts/exam.cjs check --work <W> --item <N>`을 실행하라.
✗이면 새 brief.md(고치기 모드)대로 앞 시도 문항을 고쳐 다시 check하라. ✓(awaiting_review)이면 끝이다.
담당 문항 밖 파일과 엔진 코드는 수정하지 마라. 최종 보고는 한두 줄(개념, check 횟수)로 하고, 정답·진술 내용은 적지 마라.
```

## 검토자 프롬프트 (문항마다, 출제자와 다른 새 에이전트)
```
너는 수능 직업탐구 <성공적인 직업생활|공업 일반> 검토위원이자, 정답을 모르는 수험생이다.
<W>/items/<NN>/review-brief.md 한 파일만 읽어라. 같은 폴더의 brief.md·candidate*.json·question.json·review*.json은 열지 마라.
실제 시험장에서 푸는 것처럼 진술을 하나씩 판정해 정답을 고르고 결함을 찾아라. 계산은 직접 하라.
법·제도 단원은 "법적 정합성 점검 항목"을 하나씩 대조하라. 판정이나 교과 정확성에 실제로 영향을 주는 결함만 curriculumIssues에 적어라.
dataFreeStatements에는 제시문을 가려도 교과 암기만으로 판정되는 <보기>·선지만 넣어라.
지시서 끝의 [교과서 기준] 정의로 교과 정합성을 판정하고, 스키마에 statementAnalysis·stemIssues·mixConceptsUsed가 있으면 지시대로 채워라.
결과 JSON(스키마 그대로)을 같은 폴더의 review.json에 저장하라. 기존 파일은 열지 말고 덮어써라. CLI는 실행하지 마라.
최종 보고는 한 줄(고른 정답, 난도, 지적 수)로 하라.
```

ULTRA 문항의 검토자에게는 가능하면 가장 강한 모델을 쓴다.

## 고치기 지시 (원래 출제자에게, SendMessage)
```
<N>번이 블라인드 검토에서 반려되었다. items/<NN>/brief.md(고치기 모드)를 읽고, 앞 시도 문항에서 반려 사유에 해당하는 부분만 고쳐 candidate.json으로 저장한 뒤 check하라. 다른 부분은 바꾸지 마라.
```

## 시간을 줄이는 다른 장치 (엔진에 들어 있음)
- **즉시 반려:** `check`가 블라인드 검토 전에 기계적으로 잡는다.
  - 기호 없는 빈칸
  - 실존 기업·브랜드·인물
  - 제시문을 베낀 진술
  - 성직 15·16단원에서 상시 근로자 수 누락(5명 기준으로 적용이 갈리는 제도를 판정하는 경우)
  - 해설·오답 해설의 선지 번호(①~⑤)
  - 묻지 않은 표 머리 라벨
- **고치기 모드:** 다음과 같은 반려는 명세를 유지한 채 앞 시도 문항을 고친다.
  - check 실패
  - 쉬움, 단순 읽기, 자료 없이 풀리는 진술
  - 사소한 교과 지적

  개념·자료를 바꾸는 재작성은 정답 불일치나 심각한 모호성일 때만 한다.
- **제출 전 자기 점검:** brief 끝의 7항목이다. 블라인드 검토의 반려 기준과 같다.
