# QuestionStem TPL 설계 요약

`TPL_ARTICLE`은 기사형 자료의 문단 순서를 유지하는 데 초점을 두었다. 예를 들어 기업의 생산 혁신 사례가 기사로 제시되면 제목과 본문을 분리해 보여 주고, 학생은 기사 속 활동이 어떤 개념에 해당하는지 판단한다. 문단이 빠지거나 순서가 바뀌면 사례의 원인과 결과도 달라질 수 있어 빈 문단과 순서를 함께 검사했다.

`TPL_CASE_DIAGNOSTIC_FRAME`은 하나의 상황에서 여러 조건을 확인하는 문제에 사용했다. 근로자의 계약 조건이나 기업의 경영 상황을 `case_profile`과 `narrative`에 두고, 판단해야 할 조건은 `check_items`로 나눴다. 각 항목의 체크 상태를 boolean 값으로 고정해 문자열이나 임시 표시가 들어오는 오류를 막았다.

`TPL_COMPARATIVE_MATRIX`는 표의 행과 열 자체가 판단 근거가 되는 문제를 위한 구조였다. 열에는 비교 기준을, 행에는 제도나 사례별 값을 넣었다. 열은 세 개인데 한 행의 셀이 두 개만 생성되면 값이 다른 기준 아래에 표시될 수 있어 셀 수와 열 수를 반드시 맞췄다.

`TPL_CONVERSATIONAL_FLOW`는 화자와 발화 순서가 중요한 대화형 문제에 사용했다. 참여자마다 ID와 역할을 부여하고 각 메시지가 해당 ID를 참조하게 했다. 이를 통해 사장, 근로자, 고객처럼 서로 다른 역할의 발화가 화면에서 뒤바뀌는 문제를 막았다.

`TPL_FORMAL_DOCUMENT`는 계약서, 규정과 안내문처럼 문서의 형식이 해석에 영향을 주는 문제에 사용했다. 문서 종류와 제목, 날짜, 발행처를 상단에 두고 본문은 소제목과 내용의 쌍으로 저장했다. 각주는 별도 배열로 분리해 본문과 보충 조건이 섞이지 않게 했다.

`TPL_SEQUENTIAL_WORKFLOW`는 절차의 순서나 빈 단계를 묻는 문제에 사용했다. 단계마다 번호, 이름, 설명과 빈칸 여부를 저장하고 가로·세로 방향도 함께 정했다. 이를 통해 단계가 뒤섞이거나 빈칸 위치가 바뀌는 오류를 확인할 수 있었다.

`TPL_STATISTICS`는 수치의 단위와 조사 조건이 중요한 문제에 사용했다. 제목, 출처, 조사 기간, 항목명, 값과 단위를 분리했고 필요한 경우 하위 항목도 함께 저장했다. 같은 숫자라도 `%`, `명`, `억 원`에 따라 뜻이 달라지므로 값과 단위를 한 쌍으로 검사했다.

이렇게 자료별 필드를 정하면서 표의 셀 수나 대화의 발화 순서처럼 화면에 필요한 조건을 코드로 검사할 수 있게 됐다. 다만 TPL이 확인하는 범위는 자료가 화면에 제대로 표시되는지까지였다. 발문·선택지·정답이 논리적으로 맞는지는 이후 문제 생성 과정에서 별도로 해결해야 했다.
