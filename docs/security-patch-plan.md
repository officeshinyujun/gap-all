# GAP 보안 패치 계획서

## 문서 목적

이 문서는 현재 GAP 코드베이스에서 확인된 보안 취약점을 바탕으로,
어떤 순서로 무엇을 수정해야 하는지 실행 가능한 형태로 정리한 문서다.

핵심 목표는 다음 두 가지다.

1. **즉시 위험한 항목을 빠르게 차단하는 것**
2. **세션/인증/시크릿 관리 구조를 장기적으로 안전하게 재정비하는 것**

즉, 단순한 체크리스트가 아니라
실제 개발 작업 우선순위와 배포 순서를 고려한 패치 계획서로 보는 것이 맞다.

---

## 1. 패치 방향 요약

현재 GAP 보안 패치는 아래 순서로 진행하는 것이 가장 합리적이다.

### 1단계

**비밀 노출 차단과 시크릿 교체**

### 2단계

**토큰 저장 방식과 인증 구조 개선**

### 3단계

**인증 남용 방어 및 서버 하드닝 적용**

### 4단계

**입력 검증 강화와 운영 보안 체계 보완**

이 순서가 중요한 이유는,
현재 가장 큰 리스크가 프론트 UI가 아니라
**키 유출과 세션 탈취 가능성**이기 때문이다.

---

## 2. 1차 긴급 대응 계획

### 2.1 저장소 내 비밀값 전면 회전

#### 목표

현재 저장소 안에 들어간 비밀값을 더 이상 신뢰하지 않고,
전부 폐기한 뒤 새 값으로 교체한다.

#### 대상

- `OPENAI_API_KEY`
- `OPENAI_ADMIN_KEY`
- `JWT_ACCESS_SECRET`
- `JWT_REFRESH_SECRET`
- 필요 시 `DATABASE_URL` 관련 계정 자격도 점검

#### 작업

1. 현재 사용 중인 OpenAI 키 폐기
2. 새 키 발급
3. JWT access / refresh secret 새로 생성
4. 로컬 `.env` 파일에서 실값 제거
5. `.env.example`만 남기고 실제 값은 배포 환경 변수로만 관리

#### 완료 조건

- 기존 키로는 더 이상 인증/호출이 불가능해야 함
- 코드 저장소와 문서에 실비밀이 남아 있지 않아야 함

---

### 2.2 Git 노출 정리

#### 목표

현재 커밋 이력 또는 브랜치 히스토리에 남아 있을 가능성이 있는 민감 정보 흔적을 관리한다.

#### 작업

1. `.gitignore`에 `.env`, `.env.local` 패턴 점검
2. 기존 커밋에 포함된 비밀 파일 확인
3. 필요 시 히스토리 정리 전략 수립
4. 팀원 로컬 환경에 남은 기존 키 사용 중지 공지

#### 주의

히스토리 정리는 운영 프로세스와 협업 방식에 따라 영향이 크므로,
단순 삭제보다 **키 회전이 먼저**다.

---

## 3. 인증/세션 구조 개편 계획

### 3.1 Refresh Token을 `localStorage`에서 제거

#### 목표

refresh token이 자바스크립트로 읽히지 않도록 만들어,
XSS 발생 시 세션 장기 탈취 위험을 크게 줄인다.

#### 현재 문제

- `frontend/lib/auth.ts`
- `dashboard/lib/auth.ts`

에서 access/refresh token을 모두 `localStorage`에 저장 중이다.

#### 권장 구조

- refresh token: **HttpOnly + Secure + SameSite 쿠키**
- access token: 짧은 수명 사용
- 필요 시 access token은 메모리 기반 보관

#### 작업

1. 로그인 응답에서 refresh token을 body가 아니라 secure cookie로 설정
2. refresh endpoint는 cookie에서 refresh token을 읽도록 변경
3. logout 시 cookie 무효화 처리
4. 프론트에서 refresh token 관련 로컬 저장 코드 제거

#### 완료 조건

- 브라우저 콘솔에서 refresh token을 읽을 수 없어야 함
- 로그인 / 새로고침 / 로그아웃 플로우가 새 구조에서 정상 동작해야 함

---

### 3.2 Access Token 전략 재정비

#### 목표

access token 노출 가능성을 줄이고,
세션 구조를 refresh cookie 중심으로 정리한다.

#### 권장 방향

- access token은 짧은 TTL 사용
- 가능하면 메모리 저장
- 페이지 초기화 시 `/auth/refresh` 또는 세션 복원 흐름 사용

#### 작업

1. access token 만료 시간을 현재보다 더 짧게 재설계
2. 앱 초기화 시 세션 복원 로직 정비
3. 토큰이 없을 때 유저 정보 재조회 방식 점검

---

### 3.3 JWT 시크릿 fallback 제거

#### 목표

시크릿이 없으면 서버가 기동되지 않도록 하여,
약한 기본값으로 인증이 계속 동작하는 상황을 차단한다.

#### 현재 문제

- `backend/src/auth/strategies/jwt.strategy.ts`
  - fallback 문자열 존재

#### 작업

1. `?? 'gap_access_secret'` 제거
2. 부팅 시 필수 환경변수 검증 추가
3. access / refresh secret 미설정 시 서버 시작 실패 처리

#### 완료 조건

- 필수 시크릿이 없으면 서버가 즉시 실패해야 함
- 개발/운영 환경 모두 강한 랜덤 시크릿만 사용해야 함

---

### 3.4 Refresh Token 평문 저장 제거

#### 목표

DB 유출 시 refresh token 재사용 위험을 줄인다.

#### 현재 문제

- `refresh_tokens.token` 컬럼에 원문 저장

#### 권장 구조

- refresh token은 해시 후 저장
- 서버는 들어온 refresh token을 같은 방식으로 해시해서 비교

#### 작업

1. refresh token hash 생성 유틸 추가
2. 저장 로직을 해시 저장 방식으로 변경
3. refresh / logout 조회를 해시 기준으로 변경
4. 기존 데이터 마이그레이션 또는 강제 로그아웃 정책 수립

#### 완료 조건

- DB에 refresh token 원문이 남지 않아야 함
- 기존 토큰 마이그레이션 정책이 명확해야 함

---

## 4. 인증 남용 방어 계획

### 4.1 Auth 엔드포인트 throttling 도입

#### 목표

로그인, 회원가입, refresh 요청에 대한 자동화 공격을 줄인다.

#### 대상 엔드포인트

- `POST /auth/login`
- `POST /auth/register`
- `POST /auth/refresh`
- 필요 시 `POST /auth/logout`

#### 작업

1. `@nestjs/throttler` 또는 동등한 rate limiting 계층 도입
2. IP 기반 제한 설정
3. 필요 시 이메일/계정 기준 보조 제한 추가
4. 실패 횟수 로깅 및 모니터링 추가

#### 완료 조건

- 단기간 반복 로그인 시도가 차단되어야 함
- refresh 남용도 일정 횟수 이상 제한되어야 함

---

### 4.2 관리자 및 비용성 API 보호

#### 목표

관리자 기능과 AI 생성 기능이 자동화된 과도 요청으로 악용되지 않도록 만든다.

#### 대상

- 관리자 통계/관리 API
- 시험 생성 API
- 채팅 AI 호출 API
- 복습 생성/문항 생성 API

#### 작업

1. 관리자 API 별도 rate limit 정책 적용
2. 사용자별 AI 사용량 제한 또는 quota 검토
3. OpenAI usage/admin 호출 실패 및 과다 사용 모니터링

---

## 5. 서버 보안 하드닝 계획

### 5.1 `helmet` 도입

#### 목표

브라우저 기반 공격 완화용 보안 헤더를 기본 적용한다.

#### 작업

1. `helmet` 추가
2. API 서버 기본 보안 헤더 적용
3. 프론트 배포 방식에 맞는 CSP 설계
4. iframe/embed 필요 여부에 따라 frame 정책 조정

#### 기대 효과

- 콘텐츠 스니핑 완화
- 기본 브라우저 보안 헤더 강화
- XSS/클릭재킹/잘못된 리소스 처리 관련 방어층 확보

---

### 5.2 CORS / Cookie 설정 재검토

#### 목표

쿠키 기반 인증 전환에 맞춰 CORS와 credential 정책을 함께 정비한다.

#### 작업

1. 허용 origin을 환경별로 분리
2. `credentials: true` 사용 시 실제 허용 origin만 유지
3. SameSite / Secure 정책을 환경별로 분리
4. 로컬 개발과 운영 배포 설정을 명확히 구분

---

### 6.1 `profileImageUrl` 검증 강화

#### 목표

입력 가능한 URL 범위를 명확히 제한한다.

#### 목표

현재는 즉시 취약점으로 확정하지 않았지만,
렌더링 계층이 세션 보안과 결합되면 위험해질 수 있으므로 선제 점검한다.

#### 작업

1. `react-markdown` 렌더링 정책 점검
2. HTML 허용 여부 확인

4. 필요 시 sanitize 정책 보강

## 8. 추천 구현 순서

### Phase 1 — 긴급 차단

1. 비밀값 회전
2. 저장소/히스토리 정리
3. JWT fallback 제거

### Phase 2 — 인증 구조 개편

1. refresh token cookie 전환
2. access token 전략 재설계
3. refresh token 해시 저장

### Phase 3 — 방어층 추가

1. auth throttling
2. 관리자/AI API rate limiting
3. helmet 및 기본 하드닝

### Phase 4 — 마무리 보강

1. 입력 검증 강화
2. markdown 렌더링 안전성 검토
3. 보안 로깅 및 이상 징후 탐지

## 9. 검증 방법

패치 이후에는 아래 항목을 반드시 검증해야 한다.

### 인증/세션 검증

- 로그인 성공/실패 정상 동작
- 새로고침 후 세션 유지 동작
- 로그아웃 후 세션 완전 무효화
- refresh cookie만으로 재발급 동작
- 브라우저 콘솔에서 refresh token 접근 불가

### 보안 검증

- 필수 시크릿 누락 시 서버 기동 실패
- 과도한 로그인 시도 차단
- DB에 refresh token 원문 미저장 확인
- 응답 헤더에 보안 하드닝 적용 확인

### 회귀 검증

- frontend / dashboard 모두 인증 플로우 정상 동작
- 관리자 기능 정상 동작
- 채팅/시험/복습 API가 새 인증 구조에서 깨지지 않을 것

---

## 10. 결론

현재 GAP 보안 패치는,
작은 화면 단위 수정으로 해결할 문제가 아니라
**시크릿 관리 → 세션 구조 → 인증 방어층 → 운영 보안** 순으로 재정비해야 하는 작업이다.

핵심은 아래 한 문장으로 요약된다.

> 지금 가장 먼저 고쳐야 할 것은 기능 버그가 아니라,
> 비밀값과 세션이 쉽게 탈취되거나 악용될 수 있는 구조 자체다.

이 문서의 계획대로 진행하면,
단기적으로는 노출된 위험을 빠르게 줄일 수 있고,
중기적으로는 GAP의 인증/세션 계층을 훨씬 안전한 구조로 옮길 수 있다.
